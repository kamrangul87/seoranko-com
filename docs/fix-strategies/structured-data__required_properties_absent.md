Research title: schema__required_properties_absent (topic 35).

## what's actually wrong

Structured data declares a type whose feature-specific required properties are
not all present, so the item is ineligible for that rich result.

## threshold

**There is no global required-property list.** Requirements are defined per
Search feature by Google's own page for that feature (D4), and they change.
`Article` currently has **no required properties at all** (D7) — every
Google-supported property for it is recommended.

So the threshold is per-type, sourced from a **maintained requirement table**:

| Component | Rule |
|---|---|
| required property absent | finding — item ineligible for that feature (D1) |
| recommended property absent | **informational only** — item stays eligible (D2) |
| type not in the requirement table | no finding. Absence of a table entry is not evidence of a requirement |
| type's feature is deprecated | topic 39, not this finding |

The requirement table lives in the repo, one entry per supported feature, each
with the Google feature-page URL and the date verified. A type with no entry
produces no finding — the correct behaviour when the product does not know a
feature's requirements.

**Recommended-vs-required is never blurred.** Reporting a missing recommended
property as an error is the central false positive in this topic, and it is
what most tooling does.

## detect

1. Extract structured data: JSON-LD, Microdata and RDFa (D5).
2. Read each item's `@type`.
3. Look the type up in the requirement table. No entry → skip.
4. Check required properties present and non-empty; check recommended
   properties for informational reporting only.
5. Confirm the markup is on the page it describes (D6).

## fix

Property values are content, and no model authors content applied to a
customer repo. What is deterministic:

- **required property absent but the value exists elsewhere on the page in
  machine-readable form** — a `datePublished` already in the repo's frontmatter,
  an `author.name` already in page data — scaffold from that source. Repo-sourced,
  not generated.
- **no authoritative source for the value** → `human-review` with the missing
  property named.
- **`author.name` polluted with a job title, honorific, publisher name or
  introductory words** (D14) → deterministic correction: move the extra
  information to `jobTitle`, `honorificPrefix`/`honorificSuffix`, or
  `publisher`. This is a structural fix, not content.
- **multiple authors merged into one `author` field** (D13) → deterministic
  split.
- **`Thing` or a wrong type used for a person or organization** (D15) →
  topic 37.

## postcondition

Live: the item's required properties are all present and non-empty in the
served markup. Asserted by re-extracting from the live response, not from the
repo.

## idempotent?

Yes.

## risk / blast radius

Structured data is usually generated by a shared component or a metadata
helper, so a fix applies to every page of that type. Resolve the generating
site via topic 70 — and where it is generated at build time, fix the
generator, never the output.

## rollback

Revert.

## verdict

`auto-fixable` for: `author.name` cleanup (D14), splitting merged authors
(D13), and scaffolding a required property whose value already exists in the
repo in machine-readable form.

`human-review` for any required property with no authoritative source.

`not_mechanically_fixable` for properties requiring a content or editorial
decision — an image choice, a headline, a description.

## false-positive guards

| # | Guard | Action |
|---|---|---|
| 1 | Property is recommended, not required | informational only (D2). **Never report as an error** |
| 2 | Type has no entry in the requirement table | never raise. Unknown is not non-compliant |
| 3 | `Article`, `NewsArticle`, `BlogPosting` missing `image`, `author` or dates | **all recommended** (D7, D8). Never a required-property finding |
| 4 | The feature is deprecated | topic 39 |
| 5 | Markup is on a different page than the one it describes | separate defect (D6), not an absent property |
| 6 | Requirement table entry is older than the Google page's last-updated date | stale. Re-verify before raising |
| 7 | Valid markup present but no rich result appears | expected (D3). Never a finding |
| 8 | Markup injected client-side after hydration | assess the served response (topic 67) |

### Explicitly rejected

- **A global required-property list.** D4 — requirements are per feature.
- **Treating `Article.image` as required, or applying a 1200px width
  threshold.** D7 and D10. Both stale; the second was carried in this
  project's own doctrine example and is corrected here.
- **Reporting missing recommended properties as errors.**
- **Generating property values with a language model.**
- **Inferring a requirement from schema.org.** schema.org defines vocabulary,
  not Google eligibility (D4).

## fixture

An item whose feature-table required property is absent; an `Article` with no
`image`; an `author.name` containing "posted by Dr Jane Doe, Editor"; two
authors merged in one field; a type absent from the requirement table; a
`datePublished` absent but present in repo frontmatter; valid markup with no
rich result.

CI asserts: finding for the first; **nothing** for the second; auto-fix for the
third, fourth and sixth; nothing for the fifth and seventh.
